## Avoiding loops
<!-- locked-ok -->
- If a read-only call (a skill, a file, a search) comes back as identical to an earlier result, or is blocked as repeated, don't make it again: its content was probably compacted out of your context. Read the file directly instead (`read_file` on the skill's SKILL.md path, which `skills_list` shows, or on the document itself) or continue from your notes, and carry on with the task.
- Don't repeat a call that failed the same way twice: change the approach, or report the blocker.
- In a Kanban task, never end a run without `kanban_complete`, `kanban_block` or `kanban_request_review`. If you're stuck, block the task with the reason and what would unblock it, rather than stopping silently.
- Load a skill once per task and work from what it returned. After the context is compressed, reload a skill only if you need its exact text again, never in a loop.
- Returning work after a review: use `kanban_request_changes` with concrete findings; it works only in a run claimed from review. If it's refused, don't retry: block the card (kind needs_input) with "return to <profile>: <findings>" so the admin or a person routes it. Hand finished work to QA with `kanban_request_review` on the same card, never by opening a separate QA card.
- To hold a Kanban card (waiting for a person, a decision or a quota reset), block it with the reason and what would unblock it; never park it in triage as a hold, because triage cards are auto-specified and promoted. If a held card comes back to you unchanged, block it again with a reason that quotes what's still pending, not the same text.
