## Avoiding loops
<!-- locked-ok -->
- If a read-only call (a skill, a file, a search) comes back as identical to an earlier result, or is blocked as repeated, don't make it again: its content was probably compacted out of your context. Read the file directly instead (`read_file` on the skill's SKILL.md path, which `skills_list` shows, or on the document itself) or continue from your notes, and carry on with the task.
- Don't repeat a call that failed the same way twice: change the approach, or report the blocker.
- In a Kanban task, never end a run without `kanban_complete`, `kanban_schedule` (waiting on a person, a PR, CI or a quota reset), `kanban_block` (something is broken and someone must fix it) or `kanban_request_review`. Never stop silently: the reason says what you wait for and what would move the card on.
- Handoffs move work, notes don't: when a step finishes and another role must act next (a design change that makes the architecture out of date, an approved design, a finished contract), queue a Kanban card for that role in the same turn, with the brief in its body. A comment on a done card starts nothing. Work between roles needs no approval unless your role rules name an approval step.
- Load a skill once per task and work from what it returned. After the context is compressed, reload a skill only if you need its exact text again, never in a loop.
- Returning work after a review: use `kanban_request_changes` with concrete findings; it works only in a run claimed from review. If it's refused, reassign the card to the implementer instead (`hermes kanban reassign <task> <profile>`) with a comment listing the findings; block it only if that fails too. Handing work to QA: if the work already has a Kanban card, use `kanban_request_review` on that card (reviewer: the QA profile) rather than opening a separate QA card; when your role says to create a QA card for work tracked elsewhere (a GitHub issue), create one and keep all rework on that card.
- To hold a Kanban card (waiting for a person, a decision, a PR, CI or a quota reset), park it with `kanban_schedule` and the reason; when you're woken and it's still waiting, schedule again with the same reason. Use `kanban_block` only when something is broken, and never block the same card twice for the same thing: a second block sends it to triage. Never park a card in triage as a hold: triage cards are auto-specified and promoted.
- Review rounds on documents and plans (contracts, PRDs, designs, independent reviews): when the same findings come back after one re-audit, stop cycling: record what is left as accepted trade-offs on the card (what, why, who accepted it) or block with one precise question for the owner. Never start a third round on the same findings. Fix rounds between QA and Dev on a PR are different: they go on round after round until QA passes it.
- Review findings (QA, code review, independent review, drift checks): rate each 🔴 Blocker, 🟡 Major or 🟢 Nit, with its scope and a recommendation. Answer each finding you receive with PROPOSE FIX, CONTEST (only with evidence the reviewer could read), ESCALATE (the evidence is somewhere they couldn't see) or DECLINE (a nit you won't fix), and keep a short finding-to-change list on the card.
- Posting to Discord from a Kanban worker, script or any run where `hermes send` / send_message says Discord isn't configured: use `discord-send --to <channel-or-thread-id> [--file PATH ...] --message "..."` (or the message on stdin). The running gateway delivers it with its own bot, attachments included, and the command waits and exits 0 only once delivery succeeded; it only accepts channels and threads this server already knows. Never look for or copy the bot token.
- Sharing documents with people for review, in any channel: send one final file per ticket or document, as a PDF made with `md-pdf <file.md>` (prints the PDF path; headings, tables, code and images render). Don't attach the Markdown source next to it, ZIPs, manifests, checksums or intermediate drafts: working files and evidence stay in your notes folder and go out only if someone asks for them. `discord-send` turns .md attachments into PDFs.
- Keep channels easy to follow for the humans: one message per meaningful update, not running commentary. No "starting", "working on it" or "still working" posts (the 👀 reaction already shows that). Put details, logs, evidence and file lists in your notes or on the Kanban card and link them instead of pasting them; share only final files; when several things happened, send one short summary, not a message per step. Use @here only when you need a human decision.
- When `discord-send` (or another delivery tool) reports the delivery succeeded, treat the files as received: don't ask people to confirm that files arrived, downloaded or open. Ask only for the decision or review you need.
- Kanban completion summaries: when another step will deliver the files to people, name the folder, not each file path. Hermes uploads every file path it finds in a completion summary to any chat subscribed to the card, which posts the files twice.
