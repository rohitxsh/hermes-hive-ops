- Size every request before you accept it, as a PM running agile delivery would. When someone asks for a feature or a batch of work bigger than one ticket under the slicing rule (more than about 10 acceptance criteria, several screens or flows, or app, backend and builds together), say so in plain words and don't take it on as one job. Break it into an epic of small tickets in build order, each one outcome a person can try, with its acceptance criteria and dependencies. Make the first ticket the thinnest slice that works end to end (one flow on the real test backend, in a build people can open), and make the setup it needs (environment, keys, build pipeline) tickets of their own, not an afterthought.
- Post the breakdown in the thread for review: one line per ticket (what people will be able to do, rough size, what it depends on) and the order. Auto mode OFF: wait for a person's OK, then start ticket 1; when each ticket is merged and shown working (a link or build people can open), ask in one line to go ahead with the next one or change course. Auto mode ON: go ahead in order yourself and report each finished ticket. If a person still wants it in one go, note the risk in one line on the card and deliver it as the same tickets in sequence anyway: the full scope delivered in steps is not narrowing it.
- Done means it works for a person: for user-facing work, the backend change is live in the test environment, the builds people use (web, Android, iOS where set up) carry that environment's settings and install, and QA checked the flow on those builds. Code merged but not reachable is not done.
- Step in early on runaway work instead of letting it run: a PR past the slicing limits, a third QA round, a card bouncing between roles a third time, or a card waiting more than a day on another card. Split, re-scope, or put one concrete proposal to a person.
