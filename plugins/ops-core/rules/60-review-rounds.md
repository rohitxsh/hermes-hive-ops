- Review rounds are limited. QA heads each verdict on a PR "QA round N" (count the earlier QA verdicts on that PR, across every card for it). Each finding cites the numbered acceptance criterion it breaks (or names the security hole or data loss), the steps or code path that trigger it, and a severity: **blocker** (security hole, data loss, crash, a broken acceptance criterion, a wrong result users will hit) or **minor** (edge cases unlikely in real use, polish, refactors, extra tests, docs). Races and failures that need held requests, corrupted server replies, several app engines or other conditions real users won't produce are minor unless they lose data or open a security hole.
- Round 1 is the full review: everything in one batch. Later rounds check only the fixes and what they broke; new attack tests or findings on unchanged code go to Part 2. A cross-review run during QA joins the current round. Tag a finding caused by a fix "regression from fix of <id>"; after two of those the next dev run moves up one size.
- Evidence and tooling problems are not rounds and never send a PR back to dev: missing screenshots, CI or board bookkeeping, PR wording, test-runner crashes, safety refusals. QA fixes or retries them itself, or notes them in the verdict.
- Re-checks are proportional: for a fix under about 200 changed lines, the targeted tests plus CI; the full suite once before the final pass. Keep each verdict under about 300 words, long evidence in a linked file.
- Limits: from round 3, only blockers keep a PR in rework; when only minor findings remain, QA passes it and opens one "Part 2: <title>" card or issue listing them, linked from the PR. After round 5 with blockers still open: auto mode OFF, ask a person in the thread whether to continue, split or stop, and block the card until someone answers; auto mode ON, split yourselves when the blockers sit in a part that can be cut or switched off (ship the rest, that part goes to Part 2), otherwise block for a person and say so in the next update. Round 10 is a hard stop: block the card for a person with what passes, what still fails and why it keeps failing.
- Fixing QA findings needs no approval: dev fixes them on the same PR and QA re-checks, within these limits. Ask people only when a finding would change the agreed scope or acceptance criteria. If the same finding fails after two fixes, consult the team's architect to settle the expected behaviour.
- Implementers: don't apply review or QA feedback blindly. Check each finding first: reproduce it or trace the code path, and judge whether it can really happen (reachable input, realistic conditions, the current design) and how much it would matter. Fix the real ones. For the rest, reply on the PR finding by finding with your evidence: not reproducible (what you tried), can't occur in practice (why), valid but minor (moved to Part 2), or out of scope (where it belongs). QA accepts the reply or answers with a concrete reproduction; a disagreement still open after one exchange goes to a person (auto mode off) or the team lead (auto mode on).
