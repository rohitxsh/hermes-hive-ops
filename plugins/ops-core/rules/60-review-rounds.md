- Review rounds are limited. QA heads each verdict on a PR "QA round N" (count the earlier QA verdicts on that PR, across every card for it) and gives each finding a severity with the steps or code path that trigger it: **blocker** (security hole, data loss, crash, a broken acceptance criterion, a wrong result users will hit) or **minor** (edge cases unlikely in real use, polish, refactors, extra tests, docs).
  - From round 3, only blockers keep a PR in rework. When only minor findings remain, QA passes it and opens one follow-up card or issue "Part 2: <title>" listing them, linked from the PR, so what works ships.
  - After round 5 with blockers still open: auto mode OFF, ask a human team member in the thread whether to continue, split or stop, and block the card until someone answers. Auto mode ON, split it yourselves when the blockers sit in a part that can be cut or switched off (ship the rest, move that part to a Part 2 card); otherwise block the card for a person and say so in the next update.
  - Round 10 is a hard stop: no 11th round. Block the card for a person with a short summary: what passes, what still fails, and why it keeps failing.
- Every finding cites the numbered acceptance criterion it breaks (or names the security hole or data loss). Races and failures that need held requests, corrupted server replies, several app engines or other conditions real users won't produce are minor unless they lose data or open a security hole.
- Round 1 is the full review: list everything in one batch. Later rounds check only the fixes and what they broke; new attack tests or new findings on unchanged code go to Part 2, not into the PR. A cross-review's findings join the current round instead of starting a new one. Tag a finding caused by a fix "regression from fix of <id>"; after two such regressions the next dev run moves up one size.
- Evidence and tooling problems are not rounds and don't send a PR back to dev: missing screenshots, CI or board bookkeeping, PR wording, test-runner crashes, safety refusals. QA fixes or retries those itself, or notes them in the verdict.
- Re-checks are proportional: for a fix under about 200 changed lines, run the targeted tests plus CI; run the full suite once before the final pass. Keep each verdict under about 300 words and put long evidence in a linked file.
- Implementers: don't apply review or QA feedback blindly. Check each finding first: reproduce it or trace the code path, and judge whether it can really happen (reachable input, realistic conditions, the current design) and how much it would matter. Fix the real ones. For the rest, reply on the PR finding by finding with your evidence: not reproducible (what you tried), can't occur in practice (why), valid but minor (moved to Part 2), or out of scope (where it belongs). QA accepts the reply or answers with a concrete reproduction; a disagreement still open after one exchange goes to a person (auto mode off) or the team lead (auto mode on).
