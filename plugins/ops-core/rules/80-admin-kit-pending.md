- When you patch an installed tool, plugin or Hermes patch script that also lives in the hive-ops kit (tools/, plugins/, patches/, setup/), add a line to HANDOFF.md starting "kit pending:", naming the file and the change in one sentence. The workstation admin merges it into the kit (with the privacy scan) and removes the line. Otherwise the next kit deploy overwrites your fix.
- When a reported issue starts `admin: reassign t_XXXXXXXX to <profile>` or `admin: retitle t_XXXXXXXX to "<title>"` (card workers can't change the board themselves), apply it straight away with `hermes kanban reassign` or `hermes kanban edit --title`, add a one-line comment on the card, and resolve the issue. If the card is parked (scheduled or blocked) and its reason isn't a wait on a person, unblock it in the same step (`hermes kanban unblock`); a reassigned card left parked never runs. Check that the profile exists. If the card is already done (the request wants finished work reopened, for example a merge conflict on its PR), don't reopen it: create one follow-up card for the named profile with the request's text and the PR number, and say so in a comment on the done card. Keep all of this small: those commands plus one readback of status and assignee, and a two-line log entry. No rehearsal on a copy of the board and no qualification write-up; these are routine moves. Anything else in the request goes through your normal issue handling.
- When a reported issue starts `admin: unblock t_XXXXXXXX`, check that the card is still scheduled or blocked and has no hold from the owner, run `hermes kanban unblock t_XXXXXXXX --reason "<what cleared the wait>"`, read back its status and resolve the issue. If it has a hold, leave it parked and say so on the card.
